## BUG-1 地图上的抓取用时比较长

### 实测证据

1. **同一句 Overpass 查询，走代理 504、直连 2.4s**（`/tmp/t_ovp.py`）：

   | 路径 | overpass-api.de | overpass.kumi.systems |
   |---|---|---|
   | 走 HTTP_PROXY（192.168.1.210:7892） | **HTTP 504 · 10.2s** | 读超时 · 37.0s |
   | 直连（不带代理） | **30 条 · 2.4s** ✅ | 读超时 · 30.7s |

2. 试玩服务的进程环境里确实带着代理（`/proc/69790/environ`）：
   `HTTP_PROXY=http://192.168.1.210:7892`、`HTTPS_PROXY=…`，而 `NO_PROXY` 只豁免了 `localhost / .cn / .aliyuncs.com / .deepseek.com / .tencent.com …`，
   **`overpass-api.de`（德国）、`router.project-osrm.org`、`nominatim.openstreetmap.org` 都不在豁免名单里 → 全部走代理**。
   （数据源层用的是 `requests.Session`，`requests` 默认读环境变量代理：`data_sources/_common.py:build_session`。）

3. 反向对照：**Nominatim 不走代理会直接连接失败**（实测直连 `连接失败 · 15.0s`），说明三个数据源的网络可达性**不一致**，不能一刀切开/关代理。

4. 超时配置本身也是"慢"的放大器（`data_sources/overpass.py:87-97`）：服务端 QL 超时 分组 120s / 环形 240s，客户端 HTTP 超时 分组 150s / 环形 270s；失败后**端点链**还会换下一个端点重试（`retry_backoff_s=1.0`）。
   一个坏端点 = 10~37s 起步，链上再来一次，就是用户看到的"转圈几十秒到几分钟"。

5. 查询本身也不轻：`50km` 圈内四分类 8 组并集（配额各 400）在公共实例上是重查询——本机直连跑同一个 `default_fetcher`，**6 分钟以上仍未返回**（本次实测被 900s 上限截断）。

### 根因

- **A（主因，可修）**：Overpass 的请求被代理接管 → 代理链路对该站点不稳（504/超时）→ 端点链 + 长超时把它放大成"几十秒到几分钟"。
- **B（固有）**：环形/大半径四分类并集在公共 Overpass 上本来就是慢查询（冷查询 20~110s 属正常，含市区的大圈更慢）。
- **C（体验）**：抓取是**同步阻塞**在 HTTP 请求里，前端只有一个静态文案"约 20-120s"，中途没有进度、没有"先看库内结果"的分段返回。

### 修复方案（建议全做，A/B 为必做）

1. **按数据源分别决定代理**（A，最高优先级）：新增 `WHERE2GO_PROXY_<源>` 环境变量；默认口径 = Overpass/OSRM **直连**（`session.trust_env = False`）、Nominatim **保留代理**（实测直连不通）。落地位置：`_common.build_session()`。
   验收：同一 query 直连 ≤ 数秒；`/api/places?refresh=true` 冷抓取耗时可量化下降。
2. **端点链健康排序 + 快失败**（A）：单端点单次尝试超时从 150/270s 收到 30~45s，失败立刻换下一个（保留 1 次重试），并在响应里回报 `used_endpoint`。验收：坏端点场景总耗时上限从"3~5 分钟"降到"≤90s"。
3. **先返回库内、后台抓取**（C）：`/api/places` 命中库立刻返回并附 `stale=true`；未入库时返回 202 + `job_id`，前端轮询/SSE 显示进度（分组 1/8 …）。这一步工作量中等，可后置。
4. **配额与范围收敛**（B）：环形查询按"上限圆一次查 + 本地收敛"已做过对比；建议对 `0-50km` 这类含市区的分段把每组 quota 从 400 收到 150~200（城区 POI 密度极高，配额被市内占满性价比差）。
5. **预热**：入夜/低峰用 cron 跑 `python -m services.place_loader <城市> <分段>`，把热门城市分段预抓进 SQLite（库里已有先例：上海 50_100 等 6 段）。

## BUG-2 所有目的地的介绍都显示"暂无简介(LLM 未生成或调用降级)"

### 实测证据

1. 直接问库（`backend/data/where2go.db`）：

   | (起点, 分段) | 库内条数 | 简介为空 |
   |---|---|---|
   | 上海 / 50_100 | 495 | **1**（其余都补过了）|
   | 上海 / 300_500 | 470 | **433** |
   | 昆山 / 50_100 | 460 | **460**（全空）|

2. 调 `/api/places?origin=上海&band=300_500` 返回 `source=db`、**`intro_stats=null`**、`intro_pending=433`，433 条 `intro` 为空 → 前端逐条渲染成"暂无简介(LLM 未生成或调用降级,可点「补简介」重试)"。

3. LLM 侧**是好的**：同机实测 `services.intro.default_client().chat()` 一次成功，模型 `qwen3.8-max`（阿里百炼 token-plan）返回 `四明山是海拔1012米的山峰…`，耗时 8.5s；`/api/places/meta` 也报 `llm.enabled=true`。

4. 代码口径（`services/place_loader.py`）：抓取路径在落库后调 `fill_missing_intros(limit=INTRO_BATCH_LIMIT=40)`；**读库路径（`recorded is not None and not refresh`）直接 `_read_from_db` 返回，注释写明"读库路径也不会调 LLM，保证二次查询秒出"**。→ 一次抓取最多补 40 条，470 条的段位里 430 条**永远不会**自动补齐，除非用户手点「补简介」。

### 根因

- **A（主因）**：读库路径不补简介 + 抓取路径单次上限 40 条 的**组合**。首次抓取只覆盖前 40 条，之后每次"再搜索"都命中读库路径、一条都不补 → 界面上呈现"整屏都是暂无简介"。
- **B（可观测性）**：失败被静默降级（`generate_intro` 捕获一切异常返回空串），前端无法区分"LLM 没配 key / 调用失败 / 还没生成"，只能给一句含糊的兜底文案。
- **C（口径）**：`Place.intro` 只要求"一句话"，与本次功能需求"每条 2~3 句重点介绍"不一致（见功能文档，需一并处理）。

### 修复方案

1. **读库路径也补简介，但不阻塞首屏**：命中库时先返回现有数据 + `intro_pending`；若 `intro_pending>0`，由前端在拿到列表后自动调一次 `/api/places/intros`（分批、带进度），补齐后局部刷新卡片/列表 — 用户看到的是"先出结果、简介陆续补齐"。
2. **提高/取消单次上限并转后台**：`INTRO_BATCH_LIMIT` 从 40 提高（如 80）并把整段补齐放进 FastAPI `BackgroundTasks`（响应立即返回，补齐后写库），避免"点一次补 40 条"的拉锯。
3. **失败原因可见**：`fill_missing_intros` 的返回里增加 `reason`（`no_key` / `timeout` / `format` / `ok`）与 `sample_error`，`/api/places` 与 `/api/places/intros` 都带出来；前端文案从"LLM 未生成或调用降级"改成具体原因（例：`LLM 未配置 key`、`上一次调用超时`）。
4. **一次性全量回填（运维手段）**：对已入库的老分段跑 `python -m services.intro 上海 300_500`（已有 CLI，支持 `--limit/--workers`），把存量 433+460 条补齐；建议写成"低峰 cron"，顺带解决历史欠账。

## BUG-3 搜索目的地住宿用时比较长

### 实测证据（同一台机器，对试玩服务实测）

| 请求 | 耗时 | 结果 |
|---|---|---|
| `/api/stays?lat=26.9488&lng=119.9308&radius_km=5` | **4.63s** | 0 条 |
| 同上 `radius_km=8` | **15.68s** | 0 条 |
| 同上 `radius_km=30` | **68.97s** | 3 条（均在 10.6km 外）|

- 住宿检索是**单组 5 个 selector 的并集**（`tourism=hotel/guest_house/hostel/apartment/chalet`），一次 Overpass 请求，客户端超时 `STAY_REQUEST_TIMEOUT_S=30s`（`services/stays.py:62`）。冷查询失败后 `search_stays` 会捕获所有异常返回空列表。
- 结果里每条住宿还要跑 **LLM 估价 + 简介**（`price_estimate` / `intro`），首次遇到的新住宿是逐条调用的（并发数受 `DEFAULT_WORKERS` 限制）。
- 库缓存口径：`(osm_type, osm_id)` 唯一，命中 `MIN_CACHED_ROWS=1` 就不再触网 —— **但只有"搜到过"的地点才有缓存**；崇儒乡这类没搜到的，每次都从头触网。

### 根因

- **A（主因）**：与 BUG-1 同源——Overpass 走代理导致慢/失败重试；半径越大越慢（30km 69s）。
- **B**：住宿是"点开目的地才查"，属于交互路径，却用了公共实例的冷查询；没有预热、没有负结果缓存。
- **C**：LLM 估价与简介串在响应里，首次新住宿会叠加 LLM 延迟（每条约 3~9s，并发有限）。

### 修复方案

1. 修代理策略（同 BUG-1 第 1 条）；住宿路径把客户端超时从 30s 收到 ~20s，失败**快速降级并告知原因**，不让用户干等。
2. **负结果缓存（带 TTL）**：`(坐标, 半径)` 无结果时也记一条水位（如 6 小时），避免同一目的地反复触网 15~70s；库里 `stays` 表只有 172 行（全是 9/25 上海人民广场附近的），说明大量点击都是白跑。
3. **半径阶梯 + 明确告知**：从 5km 起查，空则自动退到 10km / 30km（或让用户点"扩大范围"），并把"最近的住宿在 X km 外"直接写在提示里（实测崇儒乡最近 10.6km）。
4. **LLM 估价/简介异步化或走缓存预热**：先把 OSM 结果返回给用户（名称/类型/距离），估价与简介随后补齐（与 BUG-2 的"先出结果再补文字"同一套机制）。

## BUG-4 交通路线的费用估算逻辑（杭州 → 崇儒乡 驾车 445 元偏贵）

### 现行算法（`services/routes.py:71-190`）

```
驾车: 费用 = 里程 × 8.0L/100km × 7.5元/L  +  0.7 × 里程 × 0.5元/km
            = 里程 × 0.60 元/km(油)      +  里程 × 0.35 元/km(高速过路费)   ≈ 0.95 元/km
铁路: 费用 = max(20, 直线 × 1.2 × 0.45 元/km)
飞机: 费用 = 直线 × 1.1 × 0.6 元/km + 100 元(机建燃油)
阈值: 直线 ≥100km 出铁路、≥300km 出飞机
```

### 实测（`/api/routes` 杭州 → 崇儒乡，直线 370.4km）

| 方式 | 里程 | 时长 | 费用 | 类型 |
|---|---|---|---|---|
| 驾车 | 471.6km（OSRM 真实路网） | 334 min | **448 元** | 真实路网 + 估算费用 |
| 铁路 | 370.4km（直线口径） | 231 min | **200 元** | 全估算 |
| 飞机 | 370.4km（直线口径） | 241 min | **344 元** | 全估算 |

### 根因

- **A（口径不可比，主因）**：驾车 448 元是**一台车**的总开销（油费 283 元 + 过路费 165 元），铁路 200 元 / 飞机 344 元是**一个人**的票价。四个数字并列在同一张对比表里，看起来就是"驾车比高铁贵一倍多"，但 4 人同行时反而是驾车更便宜（448/4 = 112 元/人）。需求 M4.04 本来就要求"单/双人/家庭维度总账"，现在的路线对比表**缺"人数"这个维度**。
- **B（系数偏差）**：
  - 驾车"高速占比 0.7"对**长途**尚可，但短途（<100km）大量走城市快速路/国道，过路费被高估；
  - 铁路 0.45 元/km 偏低：G 车二等座实际约 0.5~0.55 元/km（例：杭州东→霞浦 ~574km 二等座 ~300 元 ≈ 0.52 元/km），**铁路被系统性低估约 15%**；
  - 飞机 300km 阈值过短：370km 直线、且无直飞的城市（如霞浦）现实中要"飞温州/福州 + 2h 接驳"，模型给出的 241min/344 元反而"比高铁划算"，属于**模型失真**。
- **C（可读性）**：页面只给一个总价，没有费用构成（油费/过路费/票价/机建燃油），用户无法判断这个数字是怎么来的。

### 修复方案

1. **加"人数"维度**（A，核心）：路线卡片增加 1/2/4 人切换；
   - 驾车按"整车"展示并同时给出**人均**（`总价 ÷ 人数`，可乘 4 人以内）；
   - 铁路/飞机按人均 × 人数；
   - 卡片上明示口径徽标：`整车(≤4人)` / `单人票价`。
2. **口径徽标 + 一行解释**（A）：把"驾车 = 整车费用、铁路/飞机 = 单人票价"直接印在卡片和对比表头，避免误读。
3. **系数校准**（B）：铁路单价 0.45 → 0.50 元/km；驾车高速占比按里程分档（<100km：0.45；100~300km：0.6；>300km：0.7），过路费单价 0.5 → 0.45 元/km（乘用车四车道标准约 0.4~0.45）；飞机阈值 300km → 600km，未过阈值时**不显示飞机**（或显示但标"通常需中转，仅供参考"）。
4. **费用构成明细**（C）：卡片展开后列出 `油费 / 过路费 / 票价 / 机建燃油` 的分项与算式（后端已有 `cost_model`，接口直接返回分项即可）。
5. **回落现实校验**：每条估算注明"参照 12306/OTA 实际票价，本数字为经验估算"，并保留 deep-link 让用户自行核对（已有 12306/OTA 链接）。

## BUG-5 最后几次目的地的住宿都返回"该目的地周边 5 km 内暂时没有查到住宿(OSM 覆盖有限)"

### 实测证据

1. 实测崇儒乡（福建霞浦县，坐标 26.9488/119.9308）：
   - 5km → 0 条（4.63s）；8km → 0 条（15.68s）；**30km → 3 条**，全部在 **10.58~10.62km**（汉庭 / 海悦 / 速8）。
   - 即"周边确实没有 5km 内的住宿，最近的酒店在 10.6km 外的霞浦县城"——**OSM 数据是真的稀**。
2. 库层面：`stays` 表共 172 行，全部是 9/25 一次上海（31.23,121.47）5km 检索落下的市中心酒店；**崇儒乡一类目的地一行都没落库** → 每次点击都重新触网（15~70s）。
3. 代码层面（`services/stays.py:236-260`）：`search_stays` 捕获 `DataSourceError` 与所有异常后 **`return []`**；`/api/stays` 在无结果时把 `source` 一律报成 `"db"`。
   → **"Overpass 被代理打挂/超时"和"该地真的没有住宿"在接口里长得一模一样**，前端只能统一显示"OSM 覆盖有限"。

### 根因

- **A（数据）**：乡村/乡镇的 OSM 住宿覆盖天然差（`tourism=*` 命中少），5km 半径对乡镇过小。
- **B（可观测性，主因之二）**：数据源失败与空结果**不区分**，前端给的是一句放之四海皆准的兜底话术，用户既不知道是网络问题还是真没有，也没有"扩大范围/换半径"的入口。
- **C（性能）**：负结果不缓存 → 每次点开都重复 15~70s 的触网（叠加 BUG-1 的代理问题会更糟）。

### 修复方案

1. **空结果分级返回**：`search_stays` 区分 `no_data`（Overpass 正常返回 0 条）/ `datasource_error`（异常）/ `timeout`，`/api/stays` 带 `reason` + `detail`；前端文案分三档：
   - 真的没有 → "5 km 内无住宿数据；最近的住宿在约 10.6 km 外（霞浦县城），可扩大范围"；
   - 数据源失败 → "公共数据源繁忙（已重试 N 次），可点重试或直接跳 OTA 搜索"；
   - 未配置/被墙 → 明示"网络不可达"。
2. **半径自动阶梯**：5km 空 → 自动试 10km / 30km，把"扩大范围后的结果"与"距离"直接呈现（后端已有 `radius_km` 参数与 30km 上限）。
3. **负结果缓存（TTL）**：`(坐标网格, 半径) → 空` 记水位（6 小时），避免反复触网。
4. **兜底 OTA deep-link**：空结果时给"到携程/美团/Booking 搜索 <目的地> 住宿"的跳转按钮（与 M4.07 跳转预订口径一致，不抓价、不代订）。
5. **长期**：产品化阶段切高德/百度 POI（已有 ADR 评估），或用种子数据补"县城住宿"白名单（与现有滑雪/运动种子同一套机制）。
