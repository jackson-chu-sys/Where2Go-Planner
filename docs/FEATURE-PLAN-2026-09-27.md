# Where2Go · 功能修改设计（2026-09-27 神朱需求 1~4）

> 需求原文（神朱 2026-09-27）：
> 1. 重新添加 0-50KM 范围内的目的地。
> 2. 地图上显示的目的地太多太密集 → 利用网络信息 AI 推荐 3~5 个最值得去的目的地（当前分类）显示在地图上。
> 3. 地图下方以列表形式显示所有其他目的地，地图上推荐的放在最上边，每个目的地给两到三句重点介绍。
> 4. 点击目的地后信息框内应有收藏按钮，目的地可被收藏，且该目的地所属的交通路线、住宿收藏以多条目形式挂在该目的地下边。
>
> 本文是**设计**（含取舍与默认口径）；实现按此进行，若神朱对某一项有不同意见随时改。

## 功能 1：重新添加 0-50 km 分段

**改动**
- `services/bands.py`：`DISTANCE_BANDS` 最前面加 `{"key": "0_50", "label": "0-50 km", "low": 0, "high": 50}`。
  下游自动生效：`band_inner_radius_m(0_50)=0` → Overpass 退化成**单圆 50km 查询**（不再做环形差集，代码里已有该分支）；前端分段下拉、图例、范围圈都由 `/api/places/meta` 驱动，无需硬编码。
- 语义提醒：0-50km 是**含城市内部**的一档（原四档是"环形、不含城区"）。UI 上给该档加一句说明（"含市区/近郊"），避免与"50-100 km"档的理解冲突。

**取舍**
- 城区 POI 密度极高，四分类并集的每组配额（400）会被市内目标占满。建议该档把每组配额收到 150~200（见 BUG-1 方案 4）。本次先用现有配额，观察效果再调。

**验收**
- 前端出现 `0-50 km` 档；选中后可搜到目的地并入库；`pytest` 全绿。

## 功能 2：AI 推荐 3~5 个"最值得去"的目的地（当前分类）

**数据流**
```
已入库的 (城市, band, category) 目的地
  → services/recommend.py：候选压缩（名称/分类/距离/关键 OSM 标签）
  → LLM（既有 DeepSeek/Qwen，ADR-002 同一套 key）排序 + 给推荐理由
  → 落库缓存（新表 place_recommendations，按 (城市, band, category, 候选指纹) 命中）
  → GET /api/places/recommend?origin=&band=&category=&count=5
```

**要点**
- 只推荐**当前筛选分类**内的目的地（需求原文），数量默认 5、可 3~5。
- 候选压缩：最多取 80 条（按距离/名字去重），每条一行 `名称 | 分类 | 距离 | 标签摘要`，控 token；
- 输出严格 JSON（`[{place_id, rank, reason}]`），解析失败**降级**为"按距离取前 N 条 + 无理由"，并在响应里标 `degraded=true`；
- 缓存键含**候选指纹**（条数 + id 集合的 hash）：分段重新抓取后指纹变化 → 自动重新推荐；
- LLM 未配置 key 时不报错，返回降级结果 + `reason` 说明（与 BUG-2 的"原因可见"统一）。

**关于"利用网络信息"**
- 默认口径：LLM 用**自身知识 + 候选的真实标签/距离**做判断（不额外联网抓网页），响应里注明推荐依据（`basis: llm+osm_tags`）。
- 可选增强（本次不做，留接口）：推荐前对候选抓一次公开信息（Wikipedia/OSM 摘要）拼进 prompt，标 `basis: llm+web`。是否需要联网抓取请神朱定（见文末问题 1）。

**验收**
- 同一分段重复查询命中缓存（不重复烧 token）；无 key/调用失败时页面仍可用且有明确提示。

## 功能 3：地图下方列表（推荐置顶）+ 每个目的地 2~3 句重点介绍

**布局**
```
[地图区：只显示 AI 推荐的 3~5 个 pin（高亮、带名字标签）]
[列表区（地图下方，可滚动）]
  ★ AI 推荐（3~5 条，置顶）
     名称 · 分类 · 距起点 XX km    [⭐收藏] [🚗路线/住宿]
     「2~3 句重点介绍」
     「推荐理由：…」
  ───────────────
  其他目的地（N 条，按距离由近到远）
     每条同样：名称 · 分类 · 距离 + 2~3 句介绍（懒加载）+ 收藏/路线入口
```
- 地图默认**只画推荐点**；提供"显示全部目的地"开关（默认关），避免"太多太密集"。

**2~3 句介绍的生成口径（成本敏感）**
- 复用同一套 LLM 客户端，新 prompt 生成 60~120 字的"重点介绍"（亮点/适合人群/最佳季节/看点），落库缓存（新表 `place_details`，与 `Place.intro` 一句话简介共存：弹窗用一句话，列表用长介绍）。
- **懒加载**：列表先渲染名称/分类/距离（0 延迟），介绍按"可见优先"分批生成（默认每批 10 条、推荐条目优先），生成一批就地更新；提供"生成全部介绍"按钮（会提示需要几分钟）。
- 打开列表时**不阻塞地图**，不阻塞首屏。

**验收**
- 地图上只有推荐点；列表置顶推荐、其余按距离；每条都有介绍（分批补齐有进度提示）。

## 功能 4：目的地收藏按钮 + 路线/住宿收藏挂到目的地下

**前后端现状**
- 后端 `collections` 早已支持 `kind=place`（目的地的 OSM 身份 + 坐标 + 快照 summary），但前端**只有路线卡片和住宿卡片有收藏按钮**，目的地弹窗里没有 → 需求 4 的前半段 = 补一个按钮 + 状态同步。
- 收藏唯一键 `(kind, ref_key, mode)`；路线收藏里已带目的地的 `osm_type/osm_id`；住宿收藏目前只带**住宿自己**的 OSM 身份，**没有"属于哪个目的地"的信息** → 要挂载必须补父级。

**设计（不动物理表结构，最小工程量）**
- 收藏时在 `summary` 里写入父级信息（`summary.parent = {kind, ref_key, name}`；`summary` 本就是后端自由 JSON 快照，回读原样返回，无需迁移）：
  - 目的地收藏：`summary.parent` 指向自己；
  - 路线收藏：父级 = 对应目的地（`place:<osm_type>/<osm_id>` 或坐标串，与 `ref_key` 同口径）；
  - 住宿收藏：父级 = 打开该住宿所属的目的地。
- 前端收藏面板改为**两层**：
  ```
  📍 目的地名称（分类 · 距离）        [取消收藏]
     🚗 路线 · 3 条
       驾车 334min ¥448 · 铁路 231min ¥200 · 飞机 241min ¥344   [取消]
     🛏️ 住宿 · 2 条
       汉庭酒店 ¥150-350/晚 · 速8 酒店 ¥150-300/晚              [取消]
  ```
- 旧数据兜底：没有 `parent` 的收藏仍按现有"按类型分组"显示（不丢数据、不报错）。

**验收**
- 目的地弹窗能收藏/取消，收藏面板里路线与住宿**挂在目的地下方**，可逐条取消；重复收藏幂等行为不变。
