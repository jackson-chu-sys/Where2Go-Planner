# Where2Go 夜间半价调度方案(草案,待神朱审阅)

> 背景:阿里云百炼 qwen3.8-max **22:00-08:00(Asia/Shanghai)半价**。神朱要求:本项目的**所有重度工作**安排在该时段。本文为调度与执行方案,审阅批准后实施。

---

## 一、目标与边界

- **目标**:把 qwen3.8-max 的重度消耗尽量落在 22:00-08:00 半价窗,同时不牺牲白天审阅/交互体验。
- **本方案覆盖**:Where2Go 项目(数据源/后端/前端/Codex 编码/批量 LLM)。
- **不覆盖**:whats-up、滑雪监控等其它项目(它们已有各自 cron 与模型策略,如需同样调整另行方案)。

## 二、模型与"重活"分类

| 类型 | 默认模型 | 成本档 | 是否重活 |
|---|---|---|---|
| Hermes 会话/交互/审阅/规划/短问答 | qwen3.8-flash | 低 | 否(白天可做) |
| **Codex 编码**(代码/重构/批量测试) | **qwen3.8-max** | 高 | **是 → 夜间** |
| **批量 LLM 生成**(目的地库简介、POI 文案、批量归类) | qwen3.8-max(显式) | 高 | **是 → 夜间** |
| 数据抓取(Overpass/OSRM,非 LLM) | 无 | 低但占时长 | 顺带夜间(不占 token 但省带宽/错峰) |
| cron 看门狗/监控 | —/flash | 极低 | 否 |

**定义"重度" = 会显著消耗 qwen3.8-max token 的批量/长程工作**。白天原则上不启动这类任务。

## 三、执行窗口模型

```
白天 08:00-22:00    轻活:需求讨论、设计、代码审阅、验收、文档、排程
                    【闸门】神朱白天可以把"待夜间任务"投入队列
夜间窗 22:00-08:00  【自动触发】夜班执行器跑队列里的重活(用 qwen3.8-max,享半价)
早 08:00            产出汇报 → 神朱白天审阅
```

## 四、实现:夜班执行器(cron 队列)

**不是"每晚都跑全量",而是跑"待办队列"**——白天把要做的大活写进一个任务清单文件,夜班 cron 读取并依次执行,队列空则整轮跳过(0 成本)。

### 组件
1. **待办队列文件**:`/mnt/projects/Where2Go-Planner/docs/NIGHTLY-QUEUE.md`
   - 白天把重活作为条目追加(每条:标题 / 目标 / 涉及文件 / 验收)
   - 格式固定,夜班执行器能解析
2. **夜班执行器 cron**(新任务,`no_agent` 不可用,需 agent 编排 Codex):
   - 排程:`0 22 * * *`(每晚 22:00,Asia/Shanghai)——对齐半价窗起点
   - 模型:**qwen3.8-max**(执行器自身也用 max 编排,享半价)
   - 行为:读队列 → 空则 [SILENT] 跳过;非空则逐条派 Codex(`-s danger-full-access`),每条完成后把结果写回队列状态(完成/失败/需审阅)
   - 产出:清单更新 + 晨报(哪些完成/失败/需神朱决策)
   - deliver:weixin(晨间 08:00 神朱看报),失败项不自动重试,列出来等神朱
3. **配套**:队列里有跨越多条的大任务,用 `continuity=true` 让执行器记住上次进度;失败分类按 R7。

### 调度/时区注意(踩坑清单)
- 现有 cron 全部按 Asia/Shanghai 正常排程(next_run_at 均 +08:00,正确)。
- 新建夜班任务前确认排程换算正确:`0 22 * * *` = 每日 22:00 CST = 14:00 UTC。
- 半价窗是 **22:00-08:00 CST**,不是 UTC——排程字段写 `0 22 * * *`(CST)即可,勿误用 UTC 时刻。
- 白天的 cron 若会启动 qwen3.8-max 任务需迁移/暂停(见下)。

## 五、Codex 与 qwen3.8-max 的门控

- Codex 默认已是 qwen3.8-max → **夜间调度天然享半价**,无需改配置。
- 夜班执行器调 Codex 时,仍须先 `source /opt/data/.env`(keys 只在 gateway env,记忆教训)。
- 交互式 Gate(需神朱拍板的)放白天;**夜间只跑"验收标准明确、不需中途人判"的任务**。运行中 Codex 问问题(罕见,因用了窄任务描述)→ 记入失败项,晨报请神朱定夺,不夜间阻塞空转。

## 六、收益测算(示意,按优惠 50%)

假设阶段1 有三类重活:Codex 建地图骨架 / 四分类+简介批量生成 / 数据抓取预热。
- 全放白天:全额计费。
- 排夜间:token 成本 ×50%。**执行器编排 token 也享半价**(同为 max)。
- 唯一代价:产出延后到次日早晨审阅(对"先审后做"的 workflow 无实质影响,因为 Gate 本就在白天)。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 夜班跑 Codex 遇阻塞(端点挂/需人判) | 不自动重试,记失败项 → 晨报;神朱白天决定(R7 熔断) |
| 队列空时浪费 | 队列文件为空 → [SILENT] 整轮跳过,0 token |
| 半价窗外的误跑(白天手动触发) | 约定:神朱白天不手动 `cronjob run` 重活任务;执行器只排夜 |
| 会话时区错排 | 沿用现有正确时区基线,新建后核对 next_run_at(+08:00) |
| 夜间无人在线,微信看门 | 已有 token 看门狗(b0945...)每天 0/12 点检查,晨报 08:00 前 token 有效 |
