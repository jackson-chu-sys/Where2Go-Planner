## 一、GitHub 平台发布(容器包形式)

### 1.1 目标形态

用户 `docker run`(或 docker compose up)一条命令起服务,浏览器打开即用的自托管版:
- 镜像发布到 **GHCR**(ghcr.io/<user>/where2go:latest + 语义化 tag),GitHub Actions 自动构建 multi-arch(amd64/arm64,NAS 用户是 arm 场景要覆盖)。
- 数据全落单卷(SQLite + 缓存表都在 `backend/data/`),升级镜像不丢数据。
- **零内置密钥**:高德 REST/JS key、LLM key 全部用户自备,首启走向导配置。

### 1.2 首次运行配置向导(新页面 `/setup`,核心工作量)

检测到关键 env/配置缺失时,所有页面重定向到向导;向导分四步:

| 步骤 | 内容 | 校验方式 |
|---|---|---|
| ① 高德 Web 服务 key | 图文教程(注册→创建应用→Web服务 key)+ 输入框 | 后端真调一次 `geocode("北京")`,报 `status!=1` 给出 infocode 中文解释 |
| ② 高德 JS key + 安全密钥 | 同上(同应用加「Web端(JSAPI)」key,两 key 平台隔离的坑要写明,混用报 USERKEY_PLAT_NOMATCH) | 真调 JS key 校验接口或前端加载地图探活 |
| ③ LLM key(可选) | DeepSeek / 阿里百炼(OpenAI 兼容)二选一;明说「不配也能用,只是没有 AI 简介/推荐/行程」 | 发一条 1-token 测试消息 |
| ④ 完成 | 写入配置 → 重启提示或直接热生效 | — |

**配置存储拍板点(需神朱定)**:
- 方案 A(推荐):写 SQLite 新表 `AppConfig`(key 名/值/更新时间),后端读配置顺序 = env 优先 → AppConfig 兜底。优点:容器重建不丢、向导可反复改;缺点:要注意 AppConfig 永不进 API 响应/日志(照既有「key 不出响应」口径)。
- 方案 B:向导生成 `.env` 写进挂载卷。简单,但改配置要重启、文件权限坑多。

### 1.3 发布前必须清理/准备的东西(清单)

1. **⚠️ 仓库根明文凭据移除**:`AzureMapsKey.txt`、`Github_PAT.txt` 现在就在仓库根(9/30 已发现 AzureMapsKey.txt 待处置)——公开前必须删除并**轮换这两把 key**(已进过工作区就视为泄露);`意见.txt`/`需求文档.txt` 等内部文件决定去留。
2. **Dockerfile + docker-compose.yml + .env.example**(仓库现在没有 Dockerfile):python:3.13-slim、非 root 用户、healthcheck(`/api/places/meta`)、卷 `/data`。
3. **README(中英双语)**:一句话介绍、截图/GIF、quickstart、key 申请教程链接、FAQ(QPS 10021、INVALID_USER_SCODE、高德配额免费额度说明)。
4. **LICENSE 确认**(仓库已有 LICENSE 文件,发布前核一遍类型)与第三方归属说明(高德 API 使用条款、LLM 服务商条款、免责声明:价格估算/外链不代订)。
5. **GitHub Actions**:CI(pytest 全 mock 已有 1386+ 基线)+ Release workflow(打 tag → build → push GHCR)。
6. **配置面收敛审计**:把所有 `WHERE2GO_*` env 列一张表进 README(节流间隔、缓存 TTL、回填开关等),向导只暴露 3 个 key,其余给默认值。
7. **发布版 UI**(见本文件第三节)与 dev UI 用同一代码,靠 `WHERE2GO_UI_MODE=release` 切换。
8. **冒烟脚本**:容器起后自动跑「geocode→冷抓一页→出推荐」链路(可复用 tools/perf_probe.py 思路),写进 CI 的 integration job(需要 secrets 里的测试 key,或全 mock 版)。

## 二、微信小程序发布(研究结论 → 计划)

> 详细调研见 docs/research-ota-wechat-2026-10-09.md §B,此处只放决策摘要与改造计划。
> (调研子任务进行中,本节数字以调研落稿为准,回来后核对更新)

### 2.1 资质与主体(要点)

- **个人主体**可注册小程序(免费),但**不开放 web-view 组件**、类目受限;旅游/出行类目多要求企业主体,旅行社类需《旅行社业务经营许可证》——我们定位「工具-信息查询」类可避开旅游资质,但需按最新类目表核对。
- **企业主体**:认证 300 元/年,类目全,可用 web-view(业务域名需 ICP 备案 + 校验文件)。
- 后端硬约束:小程序 `request` 合法域名必须 **HTTPS + ICP 备案**——意味着要买域名、备案(个人备案 ~2-4 周)、上 SSL,后端不能再是「家里 NAS 容器」直接暴露(或需内网穿透+备案域名,不推荐生产)。

### 2.2 技术路线三选(待调研确认后拍板)

| 路线 | 改造量 | 关键限制 |
|---|---|---|
| A. 原生小程序重写前端 | 大(index.html 4600 行全部重写为 WXML/WXS;高德换**微信小程序版 SDK**,地图组件 `<map>` 是腾讯地图底图,GCJ-02 坐标恰好一致) | 体验最好、审核最稳 |
| B. web-view 套壳现有 H5 | 小(H5 基本不动,高德 JS API 在 web-view 里可用) | **个人主体不能用 web-view**;域名备案+校验;审核对套壳类较严 |
| C. uni-app/Taro 跨端 | 中(重写但可保留大量 JS 逻辑;高德有 uni-app 插件) | 折中;引入新框架违背「不新增依赖」口径,需神朱豁免 |

初步倾向:若走企业主体 → B 最快;若个人主体 → 只能 A/C(重前端)。**建议先不启动,等 GitHub 容器版发布、有真实用户反馈后再决定是否投入**(小程序还需持续运维备案域名与服务器,成本远高于容器版)。

### 2.3 若实施的前置清单

注册小程序账号 → 主体/类目核定 → 域名购买+ICP 备案 → 云服务器(或既有 NAS + frp,备案要求指向可公网访问)→ HTTPS 证书 → 高德小程序 key(与 Web/JS key 又是第三个平台)→ 前端改造 → 提审(旅游相关功能描述注意避开「代订/组团」字眼,我们只做信息与外链跳转,免责声明要保留)。

## 三、发布版 UI 精简(去技术细节,问题 6)

### 3.1 口径

同一份 index.html,用后端注入的 `ui_mode`(env `WHERE2GO_UI_MODE`,默认 `dev`,发布容器默认 `release`)控制;**dev 模式一切照旧**(夜班/开发仍需要这些数字),release 模式隐藏以下内容:

| 位置 | 现状(示例) | release 处理 |
|---|---|---|
| 状态栏 | 「来源:本地 SQLite 读库(未触网) · 抓取于 …Z · 耗时 0.01s · 待补简介 2 条(点「补简介」) · 已抓 1 轮 · 库里还有下一页(点「加载更多」) · 起点解析:高德(主路径)」 | 只留「起点 X · 分段 · 分类 · 已显示 N 条」;来源/耗时/轮次/geocoder/技术提示全隐藏;「待补简介」提示随 TASK-16 自动备齐后本身不再出现 |
| AI 推荐副标 | 「AI 推荐 5 条 · 候选 29 条 · 依据 llm+osm_tags · 模型 阿里 Qwen(…) · qwen3.8-max · 命中推荐缓存 · 长介绍还剩 25 条待生成 · 不满意可点「🔁 换一批」」 | 只留「AI 推荐 N 条」+「🔁 换一批」按钮;模型名/缓存/依据/候选数/pending 全隐藏 |
| 长介绍批次消息 | 「长介绍:本批生成 10 条 · 失败 0 条 · 还剩 9 条 · 阿里 Qwen · qwen3.8-max · 耗时 45.85s · 自动续批中…」 | TASK-16 后本就只对显示批次生成;release 下改为静默(成功无消息,失败给一句「介绍生成失败,稍后自动重试」) |
| 页面底部说明 | 开发口径的技术说明段 | release 换一段面向用户的简介+免责声明(数据来自高德;价格/时长为估算仅供参考;外链跳转不代订) |
| 弹窗/面板里的技术标注 | 「来源:高德 · POI B0IA… · GCJ-02」「真实/估算」徽标、note 字段 | POI id/坐标系隐藏;「估算」徽标**保留**(合规需要);note 精简为用户话术 |
| 补简介/继续生成介绍/暂停按钮 | 显式 LLM 操作按钮 | release 隐藏(TASK-16 自动备齐后无需手动) |

### 3.2 实现要点

- `ui_mode` 从既有 `/api/map-config`(或 `/api/places/meta`)透出,前端 `document.body.dataset.uiMode` + CSS/JS 双闸门;隐藏≠删代码,dev 排查不受影响。
- 验收:release 模式 browser QA 截图对照上表逐条核;pytest 加静态断言(release 分支存在、dev 默认不变)。
- 工作量小(0.5-1 晚),建议排在 TASK-16 之后(16 会改这些状态文案,先改 16 再收 release 避免双改)。
